# Schema audit: FK-политика и FK-индексы

**Дата:** 2026-06-01
**Контекст:** обнаружено при доработке `migration-conventions.md` (см. память `project_schema_audit`).
**Важно:** specs-knowledge аудит (`2026-06-01-specs-knowledge-audit.md`, раздел C) проверял **соответствие миграций задокументированным правилам** и расхождений не нашёл. Этот файл — про **семантическую корректность схемы** по бизнес-логике, это другой срез.
**Правило проекта:** миграции неизменяемы → все исправления только новыми ALTER-миграциями.

---

## Бизнес-логика связей (со слов владельца проекта)

- `ingredients`, `users` — самостоятельны.
- Ингредиент, использованный в рецепте/инвентаре, **удалить нельзя** (RESTRICT).
- Рецепт, на который есть заказ, **удалить нельзя** — история (RESTRICT).
- Пользователя, у которого есть заказ или который владелец бара, **удалить нельзя** (RESTRICT).
- Нет бара → нет сессии/инвентаря (CASCADE).
- favorites/ratings — удаляются вместе с пользователем и с рецептом (CASCADE).

**Общий принцип:** FK на «обладание/часть» → CASCADE; FK на самостоятельный справочник/актора → RESTRICT.

---

## A. FK с политикой, противоречащей бизнес-логике

Сейчас `ON DELETE CASCADE`, по логике должно быть `RESTRICT`:

| FK | Сейчас | Должно | Последствие текущего CASCADE |
|---|---|---|---|
| `orders.recipe_id → recipes` | CASCADE | **RESTRICT** | удаление рецепта стирает историю заказов |
| `orders.user_id → users` | CASCADE | **RESTRICT** | удаление юзера стирает его заказы (аудит) |
| `bar_inventory.ingredient_id → ingredients` | CASCADE | **RESTRICT** | удаление ингредиента молча чистит инвентарь |
| `recipe_ingredients.ingredient_id → ingredients` | CASCADE | **RESTRICT** | удаление ингредиента молча правит рецепты |

> Примечание: `recipe_ingredients.recipe_id → recipes` остаётся CASCADE (junction, связи живут с рецептом) — корректно.

**Действие:** ALTER-миграции `DROP CONSTRAINT ... ; ADD CONSTRAINT ... ON DELETE RESTRICT` для четырёх FK.

**Следствие для приложения:** удаление юзера с заказами/владением и удаление используемого ингредиента/рецепта станут блокироваться БД. Для пользователей нужен soft-delete/анонимизация, а не `DELETE`. Это осознанная позиция — зафиксировать перед применением.

## B. Отсутствие FK-индексов (новое правило #1)

PostgreSQL **не индексирует referencing-колонку FK** (в отличие от MySQL/InnoDB). Сейчас в доменных таблицах **ни одного** FK-индекса. Правило (мягкое): FK-колонка должна быть ведущей колонкой какого-либо индекса; пропуск допустим для заведомо мелких таблиц с обоснованием в комментарии.

| Таблица.колонка | Покрыта индексом? | Нужен индекс |
|---|---|---|
| `orders.session_id` | нет | да (растёт на заказ) |
| `orders.user_id` | нет | да |
| `orders.recipe_id` | нет | да |
| `favorites.recipe_id` | нет (PK ведёт по `user_id`) | да |
| `ratings.recipe_id` | нет (PK ведёт по `user_id`) | да |
| `bar_inventory.ingredient_id` | нет | да |
| `recipe_ingredients.recipe_id` | нет | пограничная (растёт при импорте) |
| `recipe_ingredients.ingredient_id` | нет | пограничная |

Закрывается в BB-8: `bar_inventory.bar_id` (ведущая в новом UNIQUE), `bars.owner_id` и `bar_sessions.bar_id` (пропуск — крошечные).

**Действие:** ALTER-миграции `CREATE INDEX idx_{table}_{col}` для незакрытых FK на растущих таблицах.

## Приоритет

1. **B (FK-индексы)** — чистая «гигиена на вырост», без поведенческих эффектов, безопасно.
2. **A (CASCADE→RESTRICT)** — меняет поведение удаления, требует решения по soft-delete юзеров до применения.

Обе задачи — отдельной фазой schema-аудита, не в BB-8.
